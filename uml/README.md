# BiteFinder UML diagrams

This folder publishes the existing UML PNG set so the diagrams can be linked
from GitHub and the project report. Images are copied without alteration from
the local generator output. This README carries the original index, class
lookup tables, relationship explanations and type-contract notes.

Use **01_overview.png** for class collaboration
and the root [data-flow diagram](../DataFlowDiagram.png) for data movement.
The three subsystem core figures and full class sheets provide further detail;
they do not all need to fit in the main report.

## Browse the images

| Location | Contents |
| --- | --- |
| Root of this folder | Overview, BIS/BRNS/BRC core diagrams, preview and notation key |
| [Managers/](Managers/) | `M_*`: complete four-manager class sheets |
| [Appendix/](Appendix/) | `A_*`: supporting classes grouped by source package |
| [Functions/](Functions/) | `F_*`: module/function sheets; these are not invented classes |

All PNGs are 3200 × 2200 pixels at 300 DPI. A landscape Word section at about
10.5 inches wide preserves readability. Keep numbered continuation sheets
together. Overview diagrams select important members; focal class sheets show
all locally declared members. Each image contains its own annotations and does
not require this README to explain its notation.

This is a published snapshot, not an automatically regenerated build artifact.
It was copied after source commit `b77e7f20c33ff8b55b10c4bc63775983d7bbc69b`.
After changing classes or collaborators, regenerate with
`python project_overview/test_uml.py`, review the output, and deliberately update
this copy. See the [generator guide](../project_overview/README.md).
Generation reads Python source without importing the application or calling APIs.

Only PNGs and this README are published here. SVGs, Mermaid source, JSON models,
source-line evidence and per-figure sidecars remain in the external local
`bitefinder-workfiles/uml/document/` folder. References to `json/` below describe
that local evidence set, not additional files in this GitHub folder.

## Relationship interpretation

Solid hollow triangle: generalisation. Dashed hollow triangle: interface realisation. Dotted line: association. Hollow diamond at the whole: aggregation. Filled diamond at the whole: composition. Dashed open arrow: use or HTTP dependency. Cardinalities appear only where the implementation supports them, never on inheritance/dependencies.
Association uses the user's dotted-line convention; standard UML normally uses a solid association line.

Detail images display up to three important source-evidenced links to avoid unreadable crossings. The complete relation labels, source lines and ownership review notes are in json/class_model.json and per-figure relation sidecars for local review; the submitted images do not depend on these files.

Python member visibility is not HTTP authorization. The HTTP edge is conditional on BRC_SERVICE_URL; in-process operator/CLI wiring can still exist. No network isolation or authenticated-only caller claim is made.

### Reviewed AI boundary details

- `AppConfig` is the dictionary returned by `BIS/support/config.py:load_config`; it is not a config class.
- `ChatHistory` follows `ChatRequestModel.history`. Profile wishes are lists of strings in the callers; the interpreter strips and validates each item and returns `list[str]`.
- `ChatDecision` contains `intent: str`, `reply: str`, `updates: dict` and `quick_replies: list`. The interpreter checks the list container but not every element's type; the diagram does not claim a stronger `list[str]` response guarantee.
- `Recommendations` contains dictionaries with `id: int` and `reason_codes: list[str]`, checked by `BRNS.ai_manager._validate_recommendation_output`; the manager can return `None` after provider failure.
- BRC cuisine replies become `dict[int, list[str]]`; outlet matching returns a permitted certificate number (`str`) or `None`. The general JSON parser promises only a list or dict.
