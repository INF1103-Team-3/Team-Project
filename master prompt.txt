You are the lead Python developer responsible for implementing the BiteFinder university project.

Your job is to build BiteFinder incrementally into a complete, working, testable CLI application while STRICTLY following the project requirements and architectural constraints below.

============================================================
PROJECT: BITEFINDER
============================================================

BiteFinder is an AI-assisted food recommendation system.

Its purpose is to help users find nearby food that satisfies multiple requirements simultaneously, including:

- Dietary requirements
- Food allergies
- Budget
- Preferred food
- Preferred cuisine
- Location
- Maximum walking time
- Restaurant opening status
- User preferences/profile

The central recommendation principle is:

FILTER what the user cannot accept
→ RANK the remaining valid options according to preferences
→ EXPLAIN why the recommendations were selected.

AI must work with real, stored, collected, or verified restaurant data.

AI MUST NOT invent restaurant facts such as:

- Restaurant names
- Menu items
- Prices
- Coordinates
- Opening hours
- Walking distance
- Walking duration
- Dietary certification
- Allergen information

If factual data is unknown, represent it explicitly as unknown/unavailable.

3. I/O MANAGER RESPONSIBILITIES

Other modules should RETURN data/messages to io_manager rather than printing directly.

4. AI MANAGER RESPONSIBILITIES

ai_manager.py is responsible ONLY for AI API interaction.

Responsibilities include:

- Build AI prompts
- Call the AI API
- Request structured JSON
- Parse AI responses
- Validate response schemas
- Retry malformed responses when appropriate
- Handle API/API-network failures gracefully
- Return validated structured dictionaries

NO DOMAIN BUSINESS LOGIC belongs inside ai_manager.py.

For example, ai_manager.py must NOT decide:

- whether an allergen is safe
- whether the budget passes
- whether walking time passes
- whether certification is valid
- whether a restaurant should be rejected

Those decisions belong in logic_manager.py.

logic_manager.py is the domain brain of BiteFinder.

It must implement:

- Hard filtering

- Multi-condition decision rules
- AI-output validation from a domain perspective
- Opening-status decisions
- Walking-time eligibility
- Recommendation ordering
- Profile-weight update rules
- Missing-information rules

At least one meaningful multi-condition rule must use structured fields produced by AI.

============================================================
HARD CONSTRAINTS
============================================================

Hard constraints MUST be deterministic Python logic.

Examples:

- Allergies
- Mandatory dietary requirements
- Explicit maximum budget
- Explicit maximum walking time
- Explicit open-now/open-at-time requirement where applicable

These constraints must NEVER become adjustable AI preference weights.

Use a conservative approach to unknown information.

FALSE
→ requirement fails

UNKNOWN
→ requirement cannot be verified

For safety-critical or mandatory requirements:

============================================================
ALLERGY RULES
============================================================

BiteFinder must never claim food is completely allergy-safe unless the available data actually supports the relevant claim.

If allergen information or cross-contamination information is unclear:

- represent it as unknown/unverified
- do not invent safety
- explain that confirmation with the restaurant may be required

AI cannot infer allergy safety.

============================================================

============================================================

Certification information must come from stored/approved source information.

Do NOT infer certification.

"No pork shown on menu"

"Halal certified."

Represent evidence status clearly.

Suggested evidence types:

official
restaurant_reported
third_party
unknown

Unknown price should be marked unavailable/unverified.

Possible forms:

SOFT PREFERENCES
============================================================

Soft preferences may include:

- Cuisine

- User profile preferences
- Previous selections
- Variety/new-food discovery

============================================================
RANKING
============================================================

Use an understandable deterministic weighted scoring algorithm initially.

Suggested starting weights:

Current cuisine / food match: 35%
User profile preference:      25%
Walking convenience:          20%
Price preference:             15%
Variety / discovery:           5%

These values should be configurable constants rather than scattered magic numbers.

Do not treat these weights as permanent requirements.

Store individual score contributions.

Example:

food_match_score
profile_score
walking_score
price_score
variety_score
total_score

This allows BiteFinder to explain why Restaurant A ranked above Restaurant B.

Use stable deterministic tie-breaking.
