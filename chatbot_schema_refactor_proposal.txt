BITEFINDER CHATBOT — PROPOSED SCHEMA AND CODE CHANGES
Date: 27 September 2026
Revision: Accepted username limit and cuisine vocabulary/confirmation rules.
Status: Proposal only. No application changes are being made.

1. SCOPE AND SOURCE OF TRUTH

This component is only the profile/preferences chatbot. Its purpose is to identify the user, gather their preferences, validate answers, support corrections, and hand the resulting profile to the project's persistence layer.

It will not search Google, retrieve restaurants, verify MUIS certification, calculate actual routes, rank restaurants, or generate restaurant recommendations. Those features belong to other parts of the project.

The team's newly agreed dictionaries supersede the earlier dictionary proposal. Preserve the exact field names supplied by the team. Do not introduce alternatives such as user_id, restaurant_id, constraints, other_preferences, or a nested text/tags object.

In particular, retain the literal key:
"other preferences(handled by google text input)"

The type proposed below for that field is plain text because the team described it as text input for later Google handling. This is a proposed type clarification, not a field rename.

2. TARGET USER RECORD

The user registry remains keyed by the generated userID:

{
    "5d015019-dfc6-43d8-a89d-2396a1421eaf": {
        "userID": "5d015019-dfc6-43d8-a89d-2396a1421eaf",
        "email": "test@gmail.com",
        "email_verified": false,
        "username": "sean",
        "preferences": {
            "location": ["punggol", "ang mo kio", "tampines"],
            "max_distance_km": 1,
            "max_travel_time_minutes": 20,
            "budget_per_person": 5,
            "dietary_requirements": ["halal", "vegan"],
            "liked_cuisines": ["western", "indian", "mexican"],
            "disliked_cuisines": ["chinese", "turkish", "malay"],
            "other preferences(handled by google text input)":
                "Spicy food at a cafe or hawker centre; food rather than drinks."
        }
    }
}

The example illustrates structure, not mandatory defaults for new accounts.

Proposed types and validation:

- userID: generated unique string; used internally, never required for sign-in.
- email: normalized unique email string; retain regex validation.
- email_verified: boolean; bypassing SMTP must not mark it true.
- username: required trimmed string, 1–50 characters, stored directly on the user record alongside userID, email, and email_verified. It is not a preference. Collect it as an account field; email remains the sign-in identifier.
- location: list of non-empty location strings. Accept comma-separated locations in local CLI mode. Trim and deduplicate case-insensitively. A completed profile should contain at least one location.
- max_distance_km: positive number, retaining the current maximum of 100 km.
- max_travel_time_minutes: positive number, retaining the corresponding maximum of 2,000 minutes.
- budget_per_person: number from 0.01 to 1,000 SGD, with at most two decimal places in local CLI input.
- dietary_requirements: list containing only halal and/or vegan. [] means the user explicitly has no dietary requirements. Never save "none" or "non-halal" as a requirement.
- liked_cuisines and disliked_cuisines: lists of lowercase canonical cuisine names from the accepted vocabulary in Section 5, not comma-separated strings in saved JSON. [] means explicitly none or no preference.
- other preferences(handled by google text input): proposed plain-text string for relevant extra preferences. An empty string means explicitly no extra preferences.

For incomplete onboarding, retain null as a temporary unanswered value. Do not confuse an unanswered field with an explicit empty list or empty string. Completed fields must have the types above. No extra completion field is proposed in the agreed user record.

3. REMOVE AND REPLACE OLD PROFILE FIELDS

- Move preferences.name (or preferences.username, if present) to the top-level user field username. Remove both name and username from preferences.
- Replace the single location string with a location list.
- Remove allergies from the active schema, questions, AI payload, validation, displays, and active saved preferences.
- Remove spice_preference as a separate field.
- Remove dining_preferences as a separate field.
- Collect relevant spice and dining details through "other preferences(handled by google text input)" instead.
- Reduce the dietary vocabulary to halal and vegan only. Remove the previous expanded dietary list and its unsupported aliases from the active contract.

The earlier five-choice spice field is superseded by the team's combined text field. Do not silently retain that old field, its mandatory question, or a hidden replacement spice key.

4. LOCATION HISTORY AND CORRECTIONS

The location list represents places the user may want to search, based on their answers and previous searches.

Proposed behavior:

- During onboarding, accept one or several areas.
- When the user explicitly adds an area, append it without discarding existing areas.
- When the user explicitly replaces or removes an area, apply that operation to the same user's list.
- Do not interpret an ordinary addition as permission to overwrite the entire history.
- A future search component can submit confirmed searched locations through the same update interface. This chatbot will not manufacture search history.
- Keep add/replace/remove instructions transient; persist only the agreed location list.

For local testing, provide explicit CLI actions such as /edit location and /add-location so changes do not depend on AI interpretation. Exact command wording can be finalized during implementation.

5. QUESTION AND VALIDATION CHANGES

Update PROFILE_FIELDS, allowed-field collections, question text, local parsing, AI response validation, format_profile(), and all relevant tests together.

Example questions:

- Account setup: "What username should I use? (1–50 characters)". Save the answer on the user record, separately from preference onboarding.
- "Which locations would you like to search around? (comma-separated areas)"
- "How far are you willing to travel? (in km or mins)"
- "What is your budget per person? (in SGD)"
- "Do you require halal or vegan options? (halal, vegan, both, or none)"
- "Which cuisines do you like? (describe your preferences, list cuisines, or say none)"
- "Which cuisines do you avoid? (describe your preferences, list cuisines, or say none)"
- "Any other preferences? (for example spicy food, cafes, hawker centres, food or drinks; or none)"

Retain 1 km ≈ 20 minutes as the approximate walking conversion. A time-only answer fills the estimated distance; a distance-only answer fills the estimated time. Explicitly supplied values are preserved, and estimates must be labelled as approximate in the display. No route data is being calculated.

For dietary answers:

- halal -> ["halal"]
- vegan -> ["vegan"]
- both -> ["halal", "vegan"]
- none -> []
- dkdk -> reject and re-prompt
- halal plus an unknown requirement -> reject the answer and request clarification; do not silently drop the unknown part

Do not reinterpret vegetarian as vegan or convert an unsupported restriction to []. These have different meanings.

Accepted cuisine vocabulary for both liked_cuisines and disliked_cuisines:

chinese, malay, indian, peranakan, indonesian, thai, vietnamese, filipino,
japanese, korean, western, italian, french, american, mexican, turkish,
middle eastern, mediterranean, fusion.

Save canonical terms in lowercase and deduplicate entries. Categories can overlap, such as western and italian, but remain separate preferences. Do not automatically expand, collapse, or infer one category from another.

Accepted input and confirmation behavior, in both AI and local CLI modes:

- Accept natural-language answers as well as comma-separated lists. For example, "I like Japanese and Korean food" becomes ["japanese", "korean"].
- For a likely typo such as "chienese", ask "Did you mean Chinese? (yes/no)" before saving. A suggestion is not an accepted preference until the user confirms it.
- If the user declines a suggestion, ask them to clarify or select a supported cuisine. Do not save the rejected suggestion or original typo.
- When several matches are plausible, show choices and ask the user to select one; do not guess.
- For a recognizable but unsupported cuisine, explain that it is outside the supported list. Let the user select another cuisine or explicitly choose to include it in "other preferences(handled by google text input)". Do not move it there automatically.
- "None" or "no preference" becomes []. An unrecognized answer never becomes [].
- If a cuisine would appear in both liked_cuisines and disliked_cuisines, ask which list the user intends before applying the conflicting change.
- Reject nonsense such as "dkdk", numeric-only entries, empty entries, and malformed lists. Do not force unrelated text into the closest supported category.
- Keep unresolved suggestions and conflicts in temporary conversation state. Preserve existing saved preferences until the proposed cuisine update is resolved; add no new persistent fields.
- In local CLI mode, use deterministic recognition of supported cuisine names in simple phrases and conservative typo suggestions. If a phrase cannot be understood reliably without AI, re-prompt with the supported choices instead of calling the API.

The username limit applies after trimming leading/trailing whitespace: 1–50 characters. Reject an overlong username and ask for a shorter one; never silently truncate it.

Free-text locations, usernames, and extra preferences need length and character checks. AI instructions should reject unclear or irrelevant interpretations, but structural validation cannot prove that all free text is meaningful. When an interpretation is uncertain, ask the user to clarify rather than invent a saved fact.

Before saving a normalized AI interpretation of free-text extra preferences, propose showing the interpreted text for confirmation. This would let the user catch a misinterpretation without adding any fields to the saved schema.

6. CHATBOT AI BEHAVIOR

The eventual AI Manager will be supplied later. Define an integration boundary now rather than committing this component to an assumed implementation.

The chatbot's optional language assistance should:

- Interpret answers and corrections into the exact agreed preference keys.
- Normalize clear expressions to supported dietary values.
- Extract relevant locations, cuisines, and additional preferences without inventing facts. Cuisine outputs must use the accepted vocabulary; the AI cannot bypass user confirmation for typo corrections, ambiguous matches, or liked/disliked conflicts.
- Return structured updates for validation before any persistence.
- Keep identity fields, verification state, and other users' profiles outside AI-editable preferences.
- Reject obsolete keys such as name, allergies, spice_preference, and dining_preferences in new AI updates instead of silently accepting an outdated response.
- Ask for clarification when data is unsupported, ambiguous, or malformed.

The AI must not write directly to JSON files. An invalid response must not partially overwrite valid preferences.

Retain OPENROUTER_MODEL, environment/file-based API key loading, and round-robin behavior while the temporary AI integration is still used. These responsibilities move to the supplied AI Manager or its adapter when integrated; they do not remain permanent IO responsibilities.

7. MANAGER SEPARATION DISCUSSED PREVIOUSLY

The Team Project Framework Brief requires procedural managers and confines print()/input() to io_manager.py. Apply that separation to this chatbot without expanding its purpose into recommendations.

io_manager.py
- Signup/resume menus, email prompts, verification-code entry, onboarding, corrections, logout, and displays.
- Type/range/required-field validation of user answers.
- Return clean typed dictionaries and user actions.
- No knowledge of JSON filenames or direct OpenRouter calls.
- All application print()/input() calls, including visible debug output, remain here.

 data_manager.py
- Read and write the user registry.
- Retrieve a user by normalized email.
- Generate/store unique IDs and enforce unique emails at the storage boundary.
- Persist only that user's validated profile changes.
- Handle file errors without crashing and preserve damaged data rather than overwriting it accidentally.
- Keep verification challenges in separate internal storage if persistence is needed; do not add undeclared verification-code fields to the agreed user dictionary.

logic_manager.py, or the team's agreed existing logic interface
- Profile-specific decisions such as merging location history and the approximate time/distance conversion.
- Rules governing permissible updates and verification-code expiry/attempts.
- It will not gain restaurant scoring, eligibility, or ranking code as part of this chatbot task.

ai_manager.py
- Provided later by the team.
- API requests, key rotation, prompt construction, response parsing, and response schema validation.
- Its chatbot-facing integration returns proposed preference updates, never direct storage mutations.

main.py
- Coordinate the menu/session and calls between modules.
- Contain no terminal input/output or storage implementation.

Maintain one authoritative definition of the agreed keys, types, and allowed dietary values, shared by the relevant validation paths. Avoid duplicated, drifting schemas.

The brief's mandatory AI processing requirement applies to the team's overall assessed application. This local profile-collection component does not demonstrate compliance with that requirement by itself. The full project must still establish the required AI -> logic -> processed-record persistence workflow when those components are integrated. Do not force restaurant processing into the chatbot merely to imitate that pipeline.

8. RETAIN EXISTING ACCOUNT AND TESTING FEATURES

- Sign up with a unique email and generated userID.
- Resume by email only.
- Retain email verification, resend cooldown, code expiry, and attempt limits.
- SMTP_BYPASS=true remains a local-testing option and does not mark the user verified.
- AI_BYPASS=true retains fixed-question CLI onboarding without a model, keys, or API calls.
- /profile displays the account username separately from the new agreed preference fields.
- /reset clears only the active user's preferences. Retain userID, email, email_verified, and username; do not ask for the username again after a preference reset.
- /logout saves and returns to the signup/resume menu for another email.
- /quit saves and exits.
- New accounts always start empty. Do not restore the old cross-account legacy-import prompt.
- Preserve structured debug events without logging credentials, verification codes, or raw AI payloads. Continue logging both travel-limit values as previously requested.

9. EXISTING DATA MIGRATION PROPOSAL

Do not delete or rewrite current user data while implementing the proposal.

When migration is authorized and implemented:

1. Back up the existing registry first.
2. Migrate each record under the same userID and email, independently.
3. Populate the top-level username from the legacy preferences.username or preferences.name. Preserve an existing non-empty top-level username. If legacy names conflict, ask that user to confirm rather than choosing blindly. Remove the old name/username keys from preferences after migration. If no usable username exists, ask for it during account setup on resume. If a legacy username exceeds 50 characters, ask the same user for a shorter username rather than truncating it.
4. Convert a non-empty legacy location string into a one-element list.
5. Keep halal and vegan requirements where valid. If old requirements contain unsupported values, flag that user's dietary answer for clarification. Never silently treat unsupported restrictions as none or discard them while claiming the migrated profile is complete.
6. Offer the same user a review of legacy spice/dining preferences as proposed text for the combined field. Do not assume consent to invent or reinterpret the combined preference.
7. Remove obsolete fields from the active schema. Do not move allergies into a hidden new field or silently turn them into general preference text. The backup preserves the old record for recovery.
8. Keep temporary verification state separate from the agreed user fields, and preserve the email_verified boolean accurately.
9. Mark unanswered replacement fields with null and ask only the outstanding questions on resume.

Retire the old single-user import helper from the normal application path. Any migration is an explicit maintenance action, not a signup feature.

10. RESTAURANT DICTIONARY: CONTRACT REFERENCE ONLY

The chatbot will not create or modify restaurant records. Preserve these field names for later integration:

name
postal_code
address
number
g_rating
g_no_reviews
cuisine
dietary
avg_price_low_sgd
avg_price_high_sgd
opening_hours
wheelchair_accessible
halal_certification

Do not add restaurant_id or rename number, cuisine, dietary, or the Google rating fields.

Confirmed conventions:

- cuisine is a list, for example ["chinese", "western"].
- dietary uses halal and/or vegan; [] represents neither declared option. Do not introduce a "non-halal" category.
- opening_hours retains weekday keys and the team's single pair format, e.g. "tuesday": ["1100", "2330"].
- A weekday value [] means closed.
- A weekday value null means unknown.
- ["0000", "2359"] is displayed as "Open 24 hours" using the team's convention.
- Do not replace the pair format with nested time-interval lists.
- wheelchair_accessible should be a JSON boolean: true or false.
- halal_certification is [] for restaurants without halal options, "official" for MUIS-backed certification, or "non-official" for the later Google-derived information.
- Do not substitute "unofficial" or "none" for the team's stated values.
- postal_code and number remain strings to preserve formatting and leading zeroes.
- The team's example shows g_rating and g_no_reviews as strings; preserve those types unless the team explicitly agrees otherwise.

The restaurant component will handle source collection and certification evidence later. Do not infer or fetch certification within this chatbot. The team still needs a convention for halal-option restaurants whose certification information is not yet known; do not automatically classify these as having no halal options.

12. VERIFICATION PLAN

Tests should establish that:

- Output keys match the team's schema exactly.
- Removed keys cannot be written through CLI answers or new AI updates.
- username is stored at the user-record level, never inside preferences; account setup and display use it consistently.
- Trimmed usernames of 1–50 characters are accepted; empty or overlong usernames are rejected without truncation.
- Both cuisine lists contain only the 19 accepted lowercase terms, with duplicates removed.
- Natural-language cuisine answers work in AI mode and supported simple phrases work without API calls in local mode.
- "chienese" requires confirmation before "chinese" is saved; rejection or cancellation leaves the saved preference unchanged.
- Ambiguous matches and liked/disliked conflicts require user resolution.
- Unsupported cuisines are offered an explicit extra-preferences option; nonsense is rejected rather than forced into a category.
- "None" and "no preference" produce [], while unrecognized input never silently clears a list.
- Preference resets and AI preference updates cannot erase or modify the account username.
- Location answers become lists; addition, deduplication, replacement, removal, and history updates remain isolated per user.
- Dietary outputs are ["halal"], ["vegan"], ["halal", "vegan"], or [].
- Unknown dietary answers such as dkdk are rejected without partial writes.
- The combined preference stays in its exact agreed field and type.
- Time/distance conversion still uses 20 minutes per kilometre.
- SMTP and AI bypass modes continue to work independently.
- Signup does not expose another user's preferences.
- Email-based resume, logout, reset, and persistence preserve user isolation.
- Migration retains backups and does not silently convert unsupported restrictions into none.
- All print()/input() calls remain in io_manager.py after separation.
- Procedural design, PEP 8 formatting, and relevant existing regression checks remain intact.
